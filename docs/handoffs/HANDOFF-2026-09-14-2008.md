# Handoff — Touch and tablet support for Voxelheim

## Objective

Make the game playable on phones and tablets. The player base is mostly on mobile; the game required WASD, a mouse, and pointer lock, so for most of its intended audience it was not "hard to play" but unplayable — the first action it asks for is one their device cannot perform.

## Key decisions

**Intent layer before any touch control.** Gameplay code consumes named intents (`primary`, `secondary`, `jump`, movement deltas…) instead of key codes and mouse buttons. Rejected the cheaper alternative — synthesizing fake key/button state so `InputManager` looked unchanged — because it means writing touch handling twice and leaves the eat gate gating a fabricated button.

**Edges are read through per-consumer cursors, not consume-on-read.** Seven consumers read the snapshot. On a shared queue, whichever ran first would starve the rest *silently* — a chat-open edge drained by the frame loop would never reach chat, with no error. User chose this over a static ownership table.

**`drain()` clears accumulated deltas as well as queued edges.** The engine already threw away mouse movement on suppressed frames; that is the only thing stopping the camera snapping when a panel closes. Once look stopped being gated on pointer lock, dropping the delta half would have reintroduced the snap.

**Jump carries press edges with timestamps, not a boolean.** Creative flight toggles on a 300ms double-tap of Space read at the top of `PlayerController.update()`, and Space is simultaneously held-ascend while flying and edge-toggle to exit. A boolean destroys both.

**Desktop quirks preserved exactly during the refactor.** The debug overlay fires while typing in chat; a right-click buffered during pause places a block after unpause. Both are latent bugs, but fixing them inside a behavior-preserving refactor destroys the only criterion that makes it verifiable. Deferred to follow-up work — do not "fix" them without deciding to.

**No throwaway spike.** The first-playable tier does the same de-risking without producing discarded code.

**Pre-game screens pulled into Tier 1** (new requirements R30–R31, not in the origin doc). Four reviewers independently caught that Tier 1 promised "start a world" while the title screen stayed mouse-only until Tier 2, making the tier's own on-device exit check unrunnable.

**Slot actions, not slot events.** The inventory handlers only ever read `e.shiftKey`, so they now take a named action (`primary` / `quickMove` / `split`) and a classifier maps mouse and touch onto it — the same separation, applied to the UI.

**A tap waits out the double-tap window only while the cursor is empty.** Holding an item, a tap can only mean "put it down" and a double-tap has nothing to quick-move, so placing stays immediate and only picking up pays the delay.

**Multiple small PRs over one large one**, at the user's request, split on tier boundaries. When CI failed on #7 for a reason fixed in #10, the fix was merged *through* the stack rather than cherry-picked, so commit SHAs stay identical and nothing conflicts at merge time.


On-device testing needs an HTTPS origin. Either a Vercel PR preview (easiest — one per PR, already building) or `cloudflared tunnel --url http://localhost:3000`. `cloudflared` is installed at `~/.local/bin/cloudflared` (not on PATH; Homebrew's directories are not writable by this user).

`/mobile-check` reports what a given device actually supports — fullscreen routes, visualViewport, safe-area insets, standalone mode.

## Open questions / blockers

**Every touch threshold is unmeasured.** 260ms double-tap, 420ms long-press, 10px move-cancel, plus the joystick and hold-to-mine timings in U6. These are exactly what the origin doc's second blocker exists to question. One session on a phone would replace guesses with numbers.

**Device performance is unmeasured and there is no prior art.** The origin's first blocker. `docs/solutions/` has nothing on meshing budgets or render-distance tuning. If the binding constraint turns out to be meshing or GC rather than draw distance, R29 is aimed at the wrong lever and U13's scope changes.

**~23 review findings remain open** from six reviewer passes over the plan. The highest-value unaddressed ones: eating has no touch producer (the eat gate reads *secondary held*, but touch's only hold emits primary and its only secondary signal is a tap edge); suppressing the synthesized canvas click removes touch's only route to fullscreen; no success criterion measures whether touch play is actually *good*, only that desktop is unchanged.

**Safe-area code is unverified.** Insets resolve to 0 in any desktop browser, so the notch path has only been tested against synthetic values.
